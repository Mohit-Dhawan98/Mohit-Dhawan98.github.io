sre-incident-env

sre-incident-env is an open environment that tests whether an AI agent can repair a production incident. The repair takes several steps in the right order, and a wrong step makes the system worse.

Kind
Agentic AI. Open source.
Stack
Python, OpenEnv, FastMCP over HTTP, Docker on a Hugging Face Space
Status
Published with baselines for four models. The hosted Space answered on 17 November 2026. I did not rerun the baselines for this page.
Code
sre-incident-env on GitHub

Why it exists

An engineer on call does two things. They work out what broke, and then they repair it without breaking something else. Many tests for agents stop at the first half and score a diagnosis.

The second half is where incidents go wrong. Restarting the service that is shouting is the natural move, and it is often the one that turns a degraded system into a dead one. This environment scores the repair.

How it works

Each incident is a graph of system states. The agent works through nine tools modeled on an on-call toolkit: it lists services, reads logs, checks metrics, reads a runbook, and then acts. A correct action moves the system toward healthy. A wrong one does nothing or moves it backward.

There are eight incidents in three difficulty tiers, with patterns drawn from real post-mortems: a JVM metaspace leak, clock drift that unsettles Raft, a Postgres disk filled by a failing archiver, and five more. Each needs four or five correct actions across several services.

The reward is computed by code, with no model call at runtime. It has seven parts. Reaching healthy is worth 0.40, and partial progress is worth up to 0.20, growing with the square of how far along the shortest path the agent got. Credit for the diagnosis is paid only if the system is healthy, so describing the bug without fixing it earns nothing for the description.

No model is close to solving it, and the two strongest are level overall while being good at different incidents. That spread is the useful part: the environment separates models that a pass or fail check would score the same.

Status and known gaps

  • Eight scenarios is a small set. Each is hand-built. Names, thresholds and version strings are randomized per run so an agent cannot memorize the fix, but the shape of each graph is fixed.
  • It is a simulation. Logs and metrics come from a state machine, not from a running cluster.
  • Two models are missing. Gemini 2.5 Pro and Flash did not converge on the multi-step tool protocol and were left out of the baseline.

The principles behind it

Score the outcome, not the explanation. Keep the reward deterministic so two runs can be compared. Give partial credit that stays well below a full repair. And never tell the agent whether it made progress, because a real system does not.
